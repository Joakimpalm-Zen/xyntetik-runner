Runner

One binary that serves, verifies, scores, adapts and trains GGUF models.

Xyntetik Runner is written from scratch in plain C for CPU (x86 AVX2/FMA, ARM NEON), CUDA and Metal. No Python, no pip, no third-party runtime, no ggml. It speaks the OpenAI Chat Completions, Responses and Anthropic Messages APIs on a loopback port, reads the GGUF files the ecosystem already produces, and writes adapters the ecosystem can already load.

Try it

Sixty seconds to a served model

Download the binary and its checksum file, verify, fetch a model, serve. The checksum line is not decoration: this project's whole culture is receipts, and it starts at the download.

The model below, granite-4.1-3b at Q8_0, is the smallest that passes the project's fidelity gate against its own BF16 parent. Alternatives and the reasoning are in the README quick start.

curl -LO https://github.com/Joakimpalm-Zen/xyntetik-runner/releases/latest/download/runner-macos-arm64
curl -LO https://github.com/Joakimpalm-Zen/xyntetik-runner/releases/latest/download/SHA256SUMS
shasum -a 256 --check --ignore-missing SHA256SUMS
chmod +x runner-macos-arm64 && mv runner-macos-arm64 runner
curl -L -o model.gguf https://huggingface.co/ibm-granite/granite-4.1-3b-GGUF/resolve/main/granite-4.1-3b-Q8_0.gguf
./runner -m model.gguf --serve
curl localhost:8080/v1/chat/completions \
  -d '{"messages":[{"role":"user","content":"Say hello in one sentence."}]}'

Testing Runner?

The project is pre-1.0 and hardware coverage is still limited; that is an invitation, not an apology. An unusual GGUF, a coding agent, an NVIDIA or Apple setup, or a model family not in the support matrix: the result is wanted, success or failure alike. Open an issue with runner --version, runner --caps, the model's exact filename and the load log. Independent reproductions of the determinism claims are credited in the docs, as the first one already is.

What Runner adds

Not a longer feature list. A set of contracts.

Runner deliberately rides llama.cpp's formats rather than competing with them: GGUF in, llama.cpp-convention adapter files in and out. An adapter Runner trains scores identically, 1.000 on its held-out eval, when served by stock llama.cpp, and community F16 adapters load straight back. Both measured, not assumed. What it adds on top are promises the ecosystem does not make.

Determinism as a hard promise

The same executable and inputs reproduce the same sampled tokens across runs and thread counts. Training reproduces the same adapter file sha256. Both are gated in CI. Independent rebuilds are explicitly outside the byte-identity claim, because compilers and ISA libm differ, and the full boundary is one page: docs/determinism-scope.md.

Scope as a promise

Supported architectures are named. Unknown ones are refused by name rather than run on a guess. Every backend claim is tied to an executable gate and pinned model evidence, and a hardware switch has a correctness contract: CPU/GPU identity belongs to a SHA-256-pinned model and execution path, and faster kernels that reassociate sums pass tolerance gates rather than inherit correctness from the backend's name.

Designed to stay on

What a resident server does while it serves nothing

Benchmarks rarely show it, so it was measured. llama-server wires the whole model into unified memory, holds it until the process dies, and its idle loop ticks at about 160 Hz. Runner keeps weights as evictable zero-copy mappings the OS can reclaim when another app needs the RAM, wakes about once every two seconds, and hands everything back on /unload or automatically with --ttl.

The flip side is real and reported: when llama-server is allowed to hold everything, its cold time to first token is faster, because residency is exactly what it buys. These are different optimization goals, not a defect. A dedicated inference box should run llama.cpp. A machine that is also your workstation is what Runner is built for.

On a discrete GPU (RTX 3070) the footprint gap disappears, both engines hold about 4 GB of VRAM loaded, and the remaining differences are idle discipline and lifecycle control: /unload returned all 4 GB of VRAM; llama-server has no unload.

What else it adds

Ordered by how much difference each makes in practice.

A shared GPU stops being first-come, first-crash

Runner processes on the same GPU share a VRAM registry. A refused load names every live holder by PID, model, bytes and uptime; --wait-for-vram turns the refusal into a bounded queue; records left by dead processes are reaped. A GPU becomes something you can schedule rather than something you hope fits.

Ask what fits before loading anything

--caps needs no model file and returns one JSON document with live RAM and VRAM, backend and GPU limits, admitted quant types and architectures, placement modes and model-count limits. --fit answers the same question for a specific file from its GGUF header, the first few megabytes, so a ranged read decides whether the rest of the download is worth starting.

Constrained decisions come with a confidence signal

choice_logprobs records each JSON-schema branch as legal alternatives, a posterior renormalized over them, and the probed probability mass. The included calibration tool turns labeled decisions into accuracy, Brier-score and ECE gates; the boundary lane records where serving conditions disagree on a tool choice with no labels at all. A power-user feature, and documented as one.

Model surgery, with provenance

--quantize with per-tensor type plans, --prune-experts for stacked MoE layouts, --merge-lora with a provenance record, --context-surgery to compile a YaRN target into a native GGUF, and --remove-sublayer to physically drop a block's attention or FFN and declare the absence in the header. Each rewrite is deterministic and reparsed before success.

Speculative decoding from four draft sources

A draft model, an n-gram lookup, the model's own MTP head where a single-block export carries one (--mtp, token-identical, measured 1.31x on code on a Threadripper and a loss on a 4-core AVX2 box, both published), and context-grounded drafts that need no weights at all.

Structured output as a sampler guarantee

--json emits one valid JSON object. JSON-Schema, Responses text.format and tool parameter schemas compile to a streaming conformance validator covering objects, arrays, enums, unions, numeric bounds, string lengths and anchored patterns. Unsupported or ambiguous constraints fail at compile time rather than being silently weakened.

Support matrix

Named, gated, and refused by name outside the list.

runner --caps publishes the architecture IDs the current binary admits. The full per-family notes, with the measured evidence behind each row, are in the README support matrix. Summary as of v0.4.8:

Backends

CPU (x86 AVX2/FMA, ARM NEON), CUDA (driver API, embedded PTX), Metal (embedded shaders, unified memory). Linux x86_64, macOS arm64, Windows x86_64 release binaries.

Architectures

llama, mistral, smollm, stablelm, qwen2, qwen3, qwen35 (Gated DeltaNet hybrid), qwen3moe, gemma3, gemma4 (dense, MoE, E-series, native tool protocol), phi3, gpt-oss, apertus, afmoe, muse-glimmer, granite, granitehybrid and nemotron_h (Mamba-2 hybrids), nemotron_h_moe. Admission is layout-specific: an unsupported tensor arrangement is refused even when the architecture ID is listed.

Formats

GGUF v2/v3, mmap host weights, standard multi-part sets. k-quants and legacy quants, MXFP4, NVFP4 with its per-tensor scale companion, the IQ1 to IQ4 codebook families. NVFP4 and IQ1 to IQ3 are CPU-only; CUDA and Metal refuse them loudly, naming the tensor and type.

Serving

OpenAI Chat Completions, Responses, legacy completions, embeddings, Anthropic Messages, SSE streaming, parallel slots, model swap and unload, prefix reuse, thinking budgets, native tool protocols for gemma4, Apertus, Harmony and atem.

Training

LoRA through the quantized base on the CPU path; the dominant backward matvec runs on CUDA behind a flag; CUDA training end to end is open work. Adapters served with --lora on CPU dense projections; GPU-resident models refuse an adapter by name.

Provenance

Replay-verifiable transcripts; Ed25519-signed, chained receipts with a one-exit-code verifier; OpenSSF Model Signing verification of the loaded GGUF by the key method.

Desktop

macOS menu bar and Windows notification-area controller.

Not implemented

Vulkan; TLS, auth and remote bind (loopback only, by design); remote or streamed GGUF parts; qwen2moe, deepseek2, kimi and MLA attention; Mamba and Jamba; MTP on GPU backends; OMS certificate and keyless signature methods; full GBNF; image and document inputs; hosted tools; response persistence; parallel tool calls on the Responses and Messages surfaces.

Where it does not win

Published as such.

The comparison on the front page has the full table. The short version of what to expect from Runner today, in its own words.

  • Prefill throughput on CUDA is 5 to 10% of llama.cpp
    llama.cpp's prefill comes from a mature tensor-core GEMM stack across every quant type. Runner's tile is 64 columns wide, and prefill is the column that decides the next piece of work.
    weak column
  • MoE decode on GPU has known-slow rows
    Qwen3-30B-A3B decodes at 72% of llama.cpp; gemma-4-26B-A4B's dual-branch MoE at 41%; the Q3_K kernel is naive and token-identical at 13%. All three rows stay in the table.
    tracked
  • Cold first token is slower when the other engine may hold everything
    3.2 s vs 0.15 s on a pressured 8 GB M1; 10.1 s vs 0.25 s at 120B on a 128 GB M5 Max. Residency is what llama-server buys, and Runner chose not to.
    by design
  • Architecture coverage is a named list
    If your model is not on it, Runner refuses it by name. llama.cpp is the ecosystem and covers far more.
    scope
  • No Vulkan, no TLS, no remote bind
    Loopback only. A reverse proxy in front is the intended route to anything else.
    not implemented
  • The 8B and 14B training ladder is open work
    The LoRA claim is measured on one base and one task. It is not a promise about other families until they are measured.
    open

How it is built

Readable in an afternoon.

Host weights stay quantized in the mapped GGUF and are dequantized while computing. CUDA copies selected weights and compute buffers to VRAM; Metal wraps the mapped weights in unified memory. The load log and --caps are the sizing sources for an exact model and machine.

The complete map, the command-line reference and the compatibility evidence are in the README; release history with each version's measurements is in the changelog.
