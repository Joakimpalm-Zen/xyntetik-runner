LoRA training

Train the file you actually ship.

A LoRA adapter is a small set of extra weights that teaches an existing model a task without rewriting the whole model. Runner trains one directly through the quantized GGUF file used for inference, the same 4-bit or 8-bit file you will serve, on the CPU, with no separate full-precision copy and no training framework. Same data, same seed, same configuration: the same adapter, byte for byte.

Why this is unusual, and why it matters

Two numerical paths is one too many.

The usual pipeline

Fine-tune through a 16-bit copy in a Python framework. Quantize the result to a 4-bit file. Serve that file in a different engine. Three tools, two numerical paths, and the thing you trained is never exactly the thing you sampled from in production.

What Runner does instead

The serving forward pass is the training forward pass. The policy you sample is the policy you train, so the train/infer mismatch that silently breaks on-policy learning cannot occur between two codepaths that are one codepath. There is no FP16 copy to keep, and no framework to install.

Adaptation as an auditable artifact

Every adapter is written beside a provenance record: base, data and adapter sha256, seed, full config, binary sha, compiler, OS and architecture. Two runs with the same inputs write the same file, gated in CI by sha256. That is a stronger statement than "repeatable within tolerance", and it is scoped to the same build on purpose.

Measured

0.69 to 1.00, on a file you can download.

Measured 2026-08-22 on Qwen3-4B-Runner-ToolUse-Q4_K_M, a public artifact whose card carries the sidecar and the training command. The claim scope is one base and one task. The 8B and 14B ladder is open work, and these numbers are not a promise about other families until they are measured.

A measurably different object, capability-equivalent on this task's supervised decisions; on the gold-completion region they coincide to about 0.0003 nat. The caveat that travels with the claim: a 4-bit merge erases the fine-tune.

--merge-lora folds an adapter into the base to produce a standalone GGUF any runtime can serve. Merging into Q8_0 or F16 keeps the 1.00, verified in stock llama.cpp. Merging into the 4-bit base returns the score to 0.69, the base's own number, because 98.55% of the weight bytes round back to the base's quantization grid. Perplexity still looks fine while it happens. A scale sweep shows survival is monotone in delta magnitude: erased through 2x, partial at 4x, full at 8x. Serve adapters with --lora, the exact form, or merge into 8-bit or better.

# train through the quantized base you will serve
./runner -m base-Q4_K_M.gguf --train data.jsonl --train-steps 200 \
    --lora-rank 8 --train-out adapter.gguf
# adapter.gguf.train.json now records base/data/adapter sha256, seed, config, binary

# serve the adapter beside the frozen base (the exact form)
./runner -m base-Q4_K_M.gguf --lora adapter.gguf --serve

# fold it into a standalone file for any GGUF runtime: 8-bit or better
./runner -m base-Q4_K_M.gguf --lora adapter.gguf \
    --merge-lora merged-Q8_0.gguf --quant q8_0

# teacher-forced logprobs for evals and rewards
./runner -m base-Q4_K_M.gguf --lora adapter.gguf -f eval.txt --score

Flags: --train, --train-steps, --lr, --train-ctx, --train-out, --save-every, --lora-rank, --lora, --lora-scale, --merge-lora, --score. Command-line reference. scripts/train-grpo-lite.py closes the loop into seeded, replayable reinforcement fine-tuning.

Run it

Three commands, one binary.

Training runs on the CPU path. The dominant matvec of the backward runs on CUDA behind a flag, and CUDA training end to end is open work. Adapters follow llama.cpp's naming convention in both directions: F16 adapters from convert_lora_to_gguf load, and the adapters Runner writes load in llama.cpp.
