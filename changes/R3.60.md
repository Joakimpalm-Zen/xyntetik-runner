- **On the CPU a prompt's bits no longer depend on the batch size** (R3.60).
  - A prompt is fed in chunks of `-b` rows. A chunk's short tail, and a MoE expert that a chunk gave fewer than 8 rows, used to take another arithmetic than the rest of the prompt, so the logits after a prompt moved in their last bits with `-b`, with where the chunks fell, and with how much of the prompt the prefix cache had kept. On a CPU-only run every product of a prompt's feed now takes the same batch route at every width, so any `-b` of 2 or more gives the same bits; decode is unchanged. A prompt repeated from the prefix cache now gets the cold feed's bits too.
  - A scoring request's rows are not reused as a prompt's. Echo, `prompt_logprobs` and `/v1/decide`'s scored tokens are fed on the decode route. Before this, a normal request that extended such a prompt kept those rows, through the slot or the shared tier, and read a decode-route prefix under its new tokens. The engine now marks the first row a scoring feed wrote. A normal request keeps the slot's rows only below the mark, and nothing at or past it is published, pinned as a named context or saved as a preamble snapshot. A decide's state is still reused by the next request; its scored tokens are fed again (`prompt_reuse` says `scored_rows`). A persisted prefix store and automatic preamble snapshots from earlier releases are misses, fed again, as are ones from the other arithmetic class (`-b 1`, the decode route, against `-b 2` and up). A recurrent entry capped at the mark is not published. Rows loaded from disk whose provenance is unknown serve only the request that asked for them: an older session image (new ones carry the mark), and an imported named snapshot, which only a request naming its context forks. Generated tokens, and an explicit resume, keep their rows as before.
  - Measured, small batch first: on gpt-oss-120b MXFP4 (CPU, 26 threads) the prompt read 1.146x as fast at `-b 64` and 1.084x at `-b 512`. On an Apple M1 the dense CPU prompt cost read 0.994x at worst (SmolLM2-1.7B Q4_K_M, 11 rounds). Identity held at `-b 64` against `-b 512` on gpt-oss-120b (two prompts) and on a dense file (seven lengths), each with a live control.
  - Not moved: the Apple GPU and CUDA keep their routes, their CPU-resident layers and host experts included. A version that changed the Apple GPU too read 0.952x on a short prompt, under its 0.97x line. Echo (`prompt_logprobs`), option scoring and `--score` keep the decode step's numbers, and so does `-b 1`, which reads a prompt one token per forward on the decode route: the trainer's numerics, which the GRPO loop's `-b 1` server is held to. CPU prompt logits differ from earlier releases in their last bits; no greedy token changed in any read.
