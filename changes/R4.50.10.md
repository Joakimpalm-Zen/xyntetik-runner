- **OLMo 2 Instruct's chat template, rendered exactly** (R4.50.10).
  - **Limits first:**
    - Its template has no tool protocol, so the OpenAI tool protocol is refused on it with a 400, never translated
      or dropped:
      - `tools`, `tool_calls` and `tool` turns on `/v1/chat/completions`;
      - `tools` and `function_call` items on `/v1/responses`;
      - `tools`, `tool_use` and `tool_result` blocks on `/v1/messages`.
    - `--info tools` reports `"tool_family":"none"`.
    - Detected only on a file whose EOS is OLMo 2's `<|endoftext|>`, because the renderer writes that token for the
      template's `bos_token` and `eos_token`. The same template on a file with other specials keeps its former
      zephyr reading. Every published file with this template (OLMo 2 Instruct 0425 1B, 1124 7B and 1124 13B) has
      `<|endoftext|>` as both its BOS and its EOS.
    - Not covered: Tulu 3's template (Llama-3.1-Tulu-3 8B, 70B and 405B, and OLMo-2-0325-32B-Instruct, which ships
      it byte for byte). It writes no BOS and ends an assistant turn with the file's own EOS, and it is still read
      as zephyr, as before.
    - The BOS is written by the template, because this family's tokenizer adds none: the publisher's tokenizer.json
      has no post-processor, and its GGUF no `add_bos_token`. So the chat encode does not prepend another: a file
      of this family that does set `add_bos_token` still gets one BOS on a chat prompt. A raw prompt is the
      caller's own text and is encoded as before.
    - The CLI's interactive chat renders each turn on its own, for every family. With this template a later turn
      there opens with the BOS.
    - The token-level check ran on a tokenizer GGUF holding the publisher file's header (its metadata, no weights).
      The full file was not on the machine that wrote this.
    - The olmo2 architecture itself is not admitted yet (R4.50.6).
  - **What it is:** a new `olmo2` template (`--chat-template olmo2`), detected from
    allenai/OLMo-2-0425-1B-Instruct's own template. Runner took it for zephyr before, which ends every turn with a
    literal `</s>` and writes no BOS. It writes every branch of the publisher's template:
    - the BOS once;
    - a system or user turn ending with a newline;
    - an assistant turn ending with the end-of-text token, then a newline unless it is the last message;
    - the generation prompt after the last message.
  - **Evidence:**
    - `scripts/template-conformance.py` gains the `olmo2` family (the publisher's template, revision 48d788ec, the
      same bytes as its GGUF's): 16 of 16 cases byte for byte and token for token. Under the zephyr rendering, all 16
      differed.
    - Its tokenizer is OLMo 3's, byte for byte (vocabulary, merges, pre-tokenizer and added tokens), which
      `tests/compatibility/tokenizer-references/olmo-3-7b-think.tokenizer-json.json` already holds against
      transformers.
    - `tests/test_template.c` pins the branches offline.
    - `tests/test_olmo2_template.py` holds on served files:
      - the refusals;
      - the BOS once with `add_bos_token` set. Before the guard, the prompt opened with two;
      - a raw prompt's BOS as before;
      - the template on a file with another EOS staying zephyr (it read olmo2 before the guard).
    - On the publisher file's own metadata (its header, no weights), through the marked render the chat surfaces
      use: detection is olmo2, and the chat prompt opens with one BOS whether `add_bos_token` is off (the
      publisher's) or forced on.
