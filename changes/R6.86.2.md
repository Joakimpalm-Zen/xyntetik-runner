- **The runner's own `expf` (`src/pmath.h`, the portable math of a `T3=1` build) no longer keeps the attention softmax's exp scalar, and a portable build's softmax gives the output it gave before, bit for bit** (R6.86).
  - Exactly what the new `expf` gives:
    - for every float that is not a NaN, the bits of the `expf` it replaced, under strict float (a T3 build) and under `-ffast-math` (a portable build of the default flags, `-DRUNNER_PORTABLE_MATH`) alike;
    - for a NaN, in every build, the input NaN quieted: its sign and payload with the quiet bit set, which is the C library's answer. So at its callers a portable build answers a NaN as the default build does. The old `expf`'s NaN depended on the compiler: a signaling NaN came back quieted or not as the compiler folded the float-double round trip, and under `-ffast-math` there was no defined answer (+0 on Apple clang).
  - And what a portable build's softmax gives: the old portable build's output, bit for bit. The exp vectorizes in a loop of its own, and the sum after it stays in the order it always had.
  - Limits:
    - A default build is unchanged: its objects are byte-identical before and after.
    - A T3 build's output does not change, except that a signaling NaN reaching `expf` now comes back quieted. Arithmetic never makes a signaling NaN; only stored bits can be one.
    - The Windows default is unchanged here. Whether it takes the portable math waits for the Windows read (R6.85): the 29 Windows CPU cells on their pins, and the prompt cost within 5%.
  - Why: on Windows the default build takes `expf` from the C runtime, whose last bits vary by Windows version. A portable build was 8 to 15% slower on a prompt there (R6.85): the portable `expf` was `(float)pm_exp_d((double)x)`, whose early returns and power-of-two loops kept the softmax's exp loop scalar.
  - What changed:
    - `p_expf` has no branch and no loop. For a float input `pm_exp_d`'s guards decide nothing: below -104 the float is +0, above 89 it is +inf, and in between the power of two is one exponent store. So x is clamped to [-104, 89] and the same operations run in the same order. A NaN is picked out by a test on its bits, not by a float compare that `-ffast-math` may fold away, and quieted from its bits. `pm_exp_d`, `tanhf` and `powf` are unchanged.
    - **A sum next to an exp stays in order in a portable build.** A loop that both calls `expf` and sums can now vectorize. Under `-ffast-math` it would then add its sum as a vector of partial sums, and the sum's last bits move. In the first version of this change that moved two Windows CPU replies off their pins at a near-tie. `src/pm_order.h`'s `PM_IN_ORDER(acc)` marks every such sum: an empty asm on the accumulator, so the add order cannot change, in a portable build only. The sums found by the compiler's report and a scan of the source:
      - the attention softmax and Clef's softmax;
      - the MoE router softmaxes (on the CPU and the host side of CUDA);
      - the vocabulary's log-sum-exps (engine and scoring);
      - the sampler's masses;
      - the hyper-connection sum.
    - The attention softmax (`softmax`, `softmax_sink`) moved to `src/softmax.h`, with the default build's `model.o` byte-identical. In a portable build its exp runs in a loop of its own, which vectorizes, and the sum follows in order.
    - The KD teacher's `(float)exp((double)lp[i])` keeps its exp in a double in a portable build. Under `-ffast-math` gcc narrowed that expression into a call of the C runtime's `expf`, which pmath.h's macros never see. It is the one call a portable build at the release's flags imported, and it is there on main too.
  - Checks:
    - `tests/test_pmath_softmax.c` (in `make test`) compares the engine's softmax and `softmax_sink` in a portable build with the softmax before this change, bit for bit. The rows: every length to 300 and the lengths around the SIMD steps to 4096, in six value shapes. Its live control: the fused loop with the new exp must differ under `-ffast-math`. Its anchor: the probabilities sum to 1.
    - `tests/test_pmath_expf.c` compares the new `expf`, in a vectorized buffer loop and in a scalar call, with one fixed noinline oracle for every float that is not a NaN, and with the quieted input for a NaN.
      - Its inputs: 60 named ones (the signed zeros, the infinities, nine NaNs, the subnormals, both clamp edges and their neighbours, the overflow and underflow edges, `pm_exp_d`'s guards and loop crossings, the ties of k's rounding) and every 256th bit pattern. `make test` runs them under strict float and under the default flags.
      - All 2^32 inputs are opt-in: `make test-pmath-expf-all` and `make test-pmath-expf-all-default`, about a minute each.
      - Its live control is a mutant, a copy with the low half of ln 2 set to 0.
    - `tests/test_pmath_callers.c` (`make test-pmath-callers`, in `make test`) builds the engine's sampler and softmax with the default flags and as a portable build of them. For five NaNs the two must decide the same.
    - `make test-pmath-vec` reads the compiler's own vectorization report for `src/model.c` in a portable build of the default flags. It requires both softmax exp loops to be vectorized and reports the SwiGLU loop. `make test` runs it with Linux gcc, and the macos and windows CI jobs with Apple clang and MinGW gcc.
    - The windows CI job runs `make test-portable-imports` on a portable build at the release's flags, beside the t3 job's strict one.
    - `make bench-pmath-loops` times the softmax and a SiLU loop, old against new, interleaved.
  - **Red first:**
    - On main's `expf`, `test-pmath-vec` failed with Linux gcc 15.2, MinGW gcc 16.2 and Apple clang. Neither softmax loop was vectorized. The SwiGLU loop was vectorized already by MinGW gcc (64-byte vectors) and by neither of the others.
    - On the first version of this change, `test-pmath-softmax` failed (the fused vector loop moved a softmax's last bit at four keys), and so did `test-pmath-callers`: a quiet NaN gave +inf, and the sampler picked the NaN token at every RNG state where the default build picks the finite one. On an RTX 5070 host, a portable build of that version left 2 of 29 Windows CPU pins at a near-tie, and a strict build returned a signaling NaN unquieted on MinGW gcc.
  - **Gated**, on an Apple M1 (Apple clang 21):
    - All 2^32 floats, under strict float and under the default flags: none differs, the 16,777,214 NaNs included.
    - `test-pmath-softmax`: 3,828 rows and 858,588 probabilities bit-identical. The control differs on 636 of 1,914 rows.
    - Portable builds of main and of this change give byte-identical `--score` files and greedy text on all 216 test fixtures that run as models: dense, the MoE kinds, DeltaNet, gemma3 and gemma4, sliding window, hyper-connections and every quant type there. So do SmolLM2-1.7B-Instruct Q4_K_M and Qwen3-4B Q4_K_M.
    - T3 runners of main and of this change give byte-identical `--score` files and greedy text on the four test fixtures and on SmolLM2-1.7B-Instruct Q4_K_M.
    - The default build's `model.o`, `sample.o`, `engine.o` and `clef.o` are byte-identical before and after.
    - `bench-pmath-loops`, 15 interleaved rounds: the softmax loop is 1.27x as fast (lowest round 1.26x), and a SiLU loop 2.14x (lowest 1.86x). The softmax's exp vectorizes, and its sum, kept in order, is now most of its time. The first version, whose sum vectorized, read 2.36x: that order is what moved the two pins.
