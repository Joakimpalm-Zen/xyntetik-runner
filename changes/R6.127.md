- **R6.117's health-wait test passes on Windows with a virtual environment's Python** (R6.127).
  - **Limits first:** a test-only fix, no change to Runner. Measured on a Windows CUDA host under the release gate's python (a venv). Linux and macOS outside a venv spawn the same interpreter as before (`sys._base_executable` equals `sys.executable` there), and inside one the base interpreter, which is enough for a child that only imports `sys` and `time`; CI shows them.
  - **Cause (`tests/test_ornith_cpu.py`):** `test_ornith_server_health_wait_fails_with_log_on_deadline` started its fake server as `sys.executable` with stderr in a kept log, killed and waited for it, then deleted the log. In a Windows venv `sys.executable` is a launcher that runs the real interpreter as its own child. `kill()` and `wait()` reached the launcher while the interpreter still held the log's handle, so the delete failed with WinError 32 (file in use). The release dry run's CUDA gate failed on it, the step's only failure among 524 cases.
  - **Fix:** both fake servers in that test start the base interpreter (`getattr(sys, "_base_executable", sys.executable)`), so the process the test kills and waits for is the one holding the log. No retry and no sleep.
  - **Evidence:** the case alone, 10 runs each, under the venv's launcher: 1 of 10 passed before (9 WinError 32; 0 of 10 in an earlier pass), 10 of 10 after. The base interpreter as `sys.executable` passed 10 of 10 before, the control. The whole file passes on Windows: 7 passed, 7 skipped (Metal only).
  - **The same pattern elsewhere in `tests/`:** none. Every other held-file child that a test kills is `runner.exe` itself, a native process. `test_ornith_timeout_scales_and_keeps_child_output` kills a `sys.executable` child on timeout too, but reads the kept log before deleting it. That case passed 10 of 10 under the launcher, so it is unchanged.
