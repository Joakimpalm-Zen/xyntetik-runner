- **Inkling 2 Mini on CUDA** (R4.48.9, work in progress).
  - **Limits first:** not yet a route. This change so far holds G1 and G2, written before the CUDA forward: `tests/test_inkling2_cuda.c` (`make test-inkling2-cuda`, a device target) checks on the tiny file with F32, BF16 and Q8_0 projections that a GPU-allowed load runs on CUDA, that every device-resident matrix and expert stack reads back equal to the host decode, that the CUDA rows are within 1e-4 of the CPU engine's and not equal to them, that they do not move with `-b` or across loads, and that a control leaving out the expert factor falls at least ten times further. It fails until the route lands.
  - `tests/inkling2_tiny.py` writes the tiny inkling2_loop file with its dense projections F32, BF16 or Q8_0; the hardening test imports it.
  - **G1, the weights on the device:** with `RUNNER_INKLING2_CUDA=1` and a GPU allowed, a fast-route load copies every matrix and both expert stacks of each layer to the device as the file stores them (an expert's factor beside its rows), or says why not and stays on the CPU (no device, the weights larger than the free memory). The switch stays until the CUDA forward lands: such an instance computes no rows yet and says so, and a default GPU load runs on the CPU as before. G1's checks pass on the device.
  - **G2a, the products on the device:** on such an instance every linear operation of a device-held view runs on the device, one batch-1 matvec a column (cuda.c's own kernels, so a column's sums do not depend on the chunk), with the expert factor applied there; the rest of the forward stays on the CPU, and the activations travel each way per product. A failed device product makes the instance refuse every forward from then on, never hand back the CPU's rows. G2's checks pass on the tiny files: the rows within 1.3e-6 of the reference engine's (relative to the largest logit) and not equal to them, byte-identical at `-b 64` and `-b 8` and across loads, and the control without the factor 0.785 away. The default stays the CPU; Metal builds carry stubs.
  - **A failed upload leaves no view marked on the device:** the views are marked held on the device only after every tensor went up, and a failure unmarks them, so an instance that falls back to the CPU computes the CPU's rows even after another instance in the process bound its weights; before, the views put before the failure kept their mark and the rows came back as NaN without a refusal. The refusal after a failed device product now rests on the instance's own flag. Check (f) injects a failed put (test-only `RUNNER_INKLING2_CUDA_TEST_PUT_FAIL`) after a successful bind and wants the fast CPU route's rows byte for byte.
  - **The row checks count values that are not finite:** the distance check skipped NaN (a compare with NaN is false), so rows of NaN could score 0 and pass; NaN and infinity are now counted by their bits and fail the distance, the invariance and the control checks, and a check of the checker itself runs first.
  - **The device test skips off CUDA builds:** `test-inkling2-cuda` exits 77 unless the build's GPU backend is CUDA (a Metal build has a device and failed every check), and on another backend `make test-inkling2-cuda` prints `inkling2 cuda: SKIP (CUDA-only backend)` and exits 0 without running it or `flock` (stock macOS has none), as the other backend-only targets do.
  - **What goes up is what the device computes:** a load puts on the device only the views its products take (a type with a device kernel; an expert factor only on NVFP4), never the token embedding (read on the host), and no expert stack under `--cpu-moe`; the other views run their products on the CPU. The room is checked after the device context, the kernel module and the products' buffers exist, with each allocation counted as the driver rounds it, and the upload happens after `-c` and the host buffers were accepted. `tests/inkling2_tiny.py --dense f16` writes a file whose projections take no device kernel; check (g) runs it, and `--cpu-moe`, near the reference engine.
  - **The device test covers what it skipped:** each device kernel (F32, BF16, Q8_0, NVFP4 with and without its factor, IQ3_XXS) runs through the device API against float64 sums of the host decode; a failed device product (test-only `RUNNER_INKLING2_CUDA_TEST_LIN_FAIL`) must refuse that forward and the next; the invariance and control checks run on all three dense types; `make clean` removes the test binary; the CPU route's note names what the opt-in switch runs now.
  - **G2b step 1, each layer's expert body on the device:** the router stays the CPU route's code on the host, and the device runs, for every used expert in ascending index, the gather of its positions, gate_up, Inkling's SwiGLU (a new kernel, CUDA's own `tanhf`/`expf`, so it agrees with the CPU's vector polynomials to rounding, not bit for bit), down and the weighted sum, as one call per layer application instead of two products per used expert. The router's arithmetic is the CPU route's, but not its input: the layer's input already comes from device products in another order of sums, so near-tie expert selections can differ from the CPU route's. A test-only observer (`ink2_set_sel_observer`) hands out each selection with its margin, for the selection-agreement figure. `--cpu-moe` keeps the body on the CPU. The weighted sum adds without atomics, one launch per expert, and the call refuses unless each launch's positions are all different. The PTX headers are regenerated with the pinned toolchain; besides the new kernel, only label numbers move.
  - **A LoRA adapter on the CUDA route:** its term is added on the host after each attention product returns, on either route; check (q) runs the tiny model with an adapter on all four attention slots (`tests/inkling2_tiny.py --lora`) and wants the CUDA rows within 1e-4 of the CPU fast route's with the same adapter, the adapter moving them, and scale 0 giving the base rows.
