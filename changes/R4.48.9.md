- **Inkling 2 Mini on CUDA** (R4.48.9, work in progress).
  - **Limits first:** not yet a route. This change so far holds G1 and G2, written before the CUDA forward: `tests/test_inkling2_cuda.c` (`make test-inkling2-cuda`, a device target) checks on the tiny file with F32, BF16 and Q8_0 projections that a GPU-allowed load runs on CUDA, that every device-resident matrix and expert stack reads back equal to the host decode, that the CUDA rows are within 1e-4 of the CPU engine's and not equal to them, that they do not move with `-b` or across loads, and that a control leaving out the expert factor falls at least ten times further. It fails until the route lands.
  - `tests/inkling2_tiny.py` writes the tiny inkling2_loop file with its dense projections F32, BF16 or Q8_0; the hardening test imports it.
  - **G1, the weights on the device:** with `RUNNER_INKLING2_CUDA=1` and a GPU allowed, a fast-route load copies every matrix and both expert stacks of each layer to the device as the file stores them (an expert's factor beside its rows), or says why not and stays on the CPU (no device, the weights larger than the free memory). The switch stays until the CUDA forward lands: such an instance computes no rows yet and says so, and a default GPU load runs on the CPU as before. G1's checks pass on the device.
  - **G2a, the products on the device:** on such an instance every linear operation of a device-held view runs on the device, one batch-1 matvec a column (cuda.c's own kernels, so a column's sums do not depend on the chunk), with the expert factor applied there; the rest of the forward stays on the CPU, and the activations travel each way per product. A failed device product makes the instance refuse every forward from then on, never hand back the CPU's rows. G2's checks pass on the tiny files: the rows within 1.3e-6 of the reference engine's (relative to the largest logit) and not equal to them, byte-identical at `-b 64` and `-b 8` and across loads, and the control without the factor 0.785 away. The default stays the CPU; Metal builds carry stubs.
  - **A failed upload leaves no view marked on the device:** the views are marked held on the device only after every tensor went up, and a failure unmarks them, so an instance that falls back to the CPU computes the CPU's rows even after another instance in the process bound its weights; before, the views put before the failure kept their mark and the rows came back as NaN without a refusal. The refusal after a failed device product now rests on the instance's own flag. Check (f) injects a failed put (test-only `RUNNER_INKLING2_CUDA_TEST_PUT_FAIL`) after a successful bind and wants the fast CPU route's rows byte for byte.
  - **The row checks count values that are not finite:** the distance check skipped NaN (a compare with NaN is false), so rows of NaN could score 0 and pass; NaN and infinity are now counted by their bits and fail the distance, the invariance and the control checks, and a check of the checker itself runs first.
  - **The device test skips off CUDA builds:** `test-inkling2-cuda` exits 77 unless the build's GPU backend is CUDA (a Metal build has a device and failed every check), and on another backend `make test-inkling2-cuda` prints `inkling2 cuda: SKIP (CUDA-only backend)` and exits 0 without running it or `flock` (stock macOS has none), as the other backend-only targets do.
  - **What goes up is what the device computes:** a load puts on the device only the views its products take (a type with a device kernel; an expert factor only on NVFP4), never the token embedding (read on the host), and no expert stack under `--cpu-moe`; the other views run their products on the CPU. The room is checked after the device context, the kernel module and the products' buffers exist, with each allocation counted as the driver rounds it, and the upload happens after `-c` and the host buffers were accepted. `tests/inkling2_tiny.py --dense f16` writes a file whose projections take no device kernel; check (g) runs it, and `--cpu-moe`, near the reference engine.
  - **The device test covers what it skipped:** each device kernel (F32, BF16, Q8_0, NVFP4 with and without its factor, IQ3_XXS) runs through the device API against float64 sums of the host decode; a failed device product (test-only `RUNNER_INKLING2_CUDA_TEST_LIN_FAIL`) must refuse that forward and the next; the invariance and control checks run on all three dense types; `make clean` removes the test binary; the CPU route's note names what the opt-in switch runs now.
  - **G2b step 1, each layer's expert body on the device:** the router stays the CPU route's code on the host, and the device runs, for every used expert in ascending index, the gather of its positions, gate_up, Inkling's SwiGLU (a new kernel, CUDA's own `tanhf`/`expf`, so it agrees with the CPU's vector polynomials to rounding, not bit for bit), down and the weighted sum, as one call per layer application instead of two products per used expert. The router's arithmetic is the CPU route's, but not its input: the layer's input already comes from device products in another order of sums, so near-tie expert selections can differ from the CPU route's. A test-only observer (`ink2_set_sel_observer`) hands out each selection with its margin, for the selection-agreement figure. `--cpu-moe` keeps the body on the CPU. The weighted sum adds without atomics, one launch per expert, and the call refuses unless each launch's positions are all different. The PTX headers are regenerated with the pinned toolchain; besides the new kernel, only label numbers move.
  - **A LoRA adapter on the CUDA route:** its term is added on the host after each attention product returns, on either route; check (q) runs the tiny model with an adapter on all four attention slots (`tests/inkling2_tiny.py --lora`) and wants the CUDA rows within 1e-4 of the CPU fast route's with the same adapter, the adapter moving them, and scale 0 giving the base rows.
  - **The expert body's tests catch what they missed:** the device check runs at the real model's widths (more than one block per kernel) with gate rows unlike their up rows and an expert with no positions, so a SwiGLU that swaps gate and up or drops its block offset fails it; a failure inside the expert call and a repeated position in a scatter list are injected (test-only) and refuse; the single-product drop is asserted against the per-product path; the selection observer is checked. The device call checks its arguments, the bind reserves the position lists and weights too, and an instance can keep the per-product body although the process's hook is set.
  - **One device copy per file, never a mixed server:** a server's `--parallel` slots are each their own instance, and each used to upload the whole file again, so the second slot found no room and ran on the CPU beside a CUDA one. Instances of one file and placement now share one refcounted device copy (freed with the last of them), and the fit decides once for all of them, counting every slot: every weight the device computes, else the expert stacks on the host (as `--cpu-moe`, with a note), else the CPU for every slot with a sentence.
  - **G2b step 2a, the attention core and the K/V cache on the device:** each instance keeps its K/V rings on the device (the host rings are freed), and each layer application's core runs there (a new kernel: one warp a query and head, a fixed order of sums, an exact two-pass softmax with the sink), while the projections, the convolutions, the norms, the relative bank and the sinks stay on the host for now. A device instance refuses rather than fall back to a host core whose cache it no longer has; a rewind re-prefills through the device rings. The fit counts every slot's rings.
  - **The device functions are each instance's own:** an instance's views and cache reach its device functions through the instance itself, so a bind in one server slot writes nothing another slot's forward reads (before, each bind set process-wide pointers while other slots' forwards read them). A fit that falls back to keeping the expert stacks on the host first frees the buffers its whole-device attempt reserved, and the load's log line gives the same host cache figure as the fit.
  - **G2b step 2b, the whole attention block on the device:** per layer application one call takes the block's inputs up and its output back: the query, key and value products, the query's and the relative states' scaled clips, the key and value convolutions over their histories (now on the device beside the K/V rings, read only past position 0), the key clip and the value norm, the relative bank, the sinks, the core, the output gate and its product. The small sums follow the CPU route's code operation for operation. An active LoRA adapter keeps step 2a's path for its sequence (an adapter appearing in the middle of a sequence the device began is refused); a file whose projections cannot go up (F16) keeps it too.
  - **On top of the CPU route's decode fusion and its default chunk of 256:** the fused decode paths never take a device's work: a group of products fuses on the host only when none of its weights is on the device, and the fused attention branch joins the shared K/V and core step, so with `RUNNER_INK2_DECODE_FUSE` on or off the device runs the same calls and the rows are the same bit for bit. The device's product output buffer holds a chunk's rows of every product but the head and one head row, since a forward asks for its last row only; a keep-all forward runs the head a group of positions at a time, which changes no bit. On the full model at the default chunk that is about 3 MB instead of about 205 MB. Every sliding K/V ring holds the window plus the chunk (window - 1 + 256 rows at the default).
  - **The device fit counts the whole attention block:** a slot's convolution histories are counted beside its K/V rings, and the block's working buffers are allocated before the free memory is read. A refused or failed block call no longer advances the slot's position: after an adapter is refused in the middle of a sequence, the sequence continues where it was without it. A model whose convolutions have one tap runs step 2a's path instead of failing on the device.
  - **The device attention core is fast at a decode step:** at one position a step the core ran one warp per head, each thread a key's whole dot product twice, which made decoding with the attention on the device slower than with it on the CPU. The core now computes every admitted key's logit once across many threads, then the softmax and the weighted values with a thread per dimension, in the same order of operations, so its results are the same bit for bit. `make bench-inkling2-cuda-core` times it against the former kernel.
  - **The device expert body runs in five launches a layer:** one gather, one gate_up product, one SwiGLU, one down product and one weighted sum over every chosen (expert, position) pair at once, instead of five launches for each used expert. Each product keeps its former per-column arithmetic and each position still adds its experts in ascending order, so the results are the same bit for bit.
  - **BF16 products of 16 positions or more run batched:** a BF16 product over at least 16 positions now runs as one launch that applies each decoded weight to 16 positions at once, instead of one launch a position. (Batching the expert body's BF16 products measured slower than its per-position launch, so BF16 experts stay per position.)
  - **The loop's message gates run as one device call a step:** each message step (its norms, its three products per role and the gated combination) runs on the device in one call, instead of each product travelling to the device and back on its own. The CPU route's tanh there is reproduced on the device exactly, so the results are the same bit for bit (in a binary that keeps subnormal numbers, as the strict build does; the default build's flush-to-zero mode can differ for subnormal values only). Each position's sum is the same as before, bit for bit; prefill and scoring get faster, and a decode step is unchanged.
  - **NVFP4 products of 16 positions or more run batched too:** each decoded NVFP4 weight is applied to 16 positions at once, in the dense products and in the expert body, with every position's sum in the former per-position order, so the results are the same bit for bit. The NVFP4 product was limited by its decoding work, not by memory; this spreads that work over the positions of a chunk. Its first version read every position's input from device memory once for each row and made prefill twice as slow; the batched kernel now shares a staged copy of the inputs between the rows of a block, as the single-position kernel does, and prefill is a quarter faster than before the batching.
  - **The expert router runs on the device for chunks of positions:** for a chunk of two positions or more, each expert layer's router (its scores, the choice of the eight experts and their weights) and the body's tables now run on the device in the same call as the expert body, instead of the scores and choices being made on the CPU and sent across; prefill is 11% faster. A single position (a decode step) keeps the CPU's router, which is faster there. The device router reproduces the CPU's arithmetic operation for operation, its sigmoid and its handling of ties and NaN included, so the chosen experts and the rows are the same bit for bit either way.
  - **A decode step runs whole on the device:** at one position, the 48 layer applications run on the device in one call. That covers the reads of the block states, the message gates, the norms, the attention block, both post convolutions, the router (on the device at one position too) and the expert body, then the final read, the head and the softcap.
    - Per step only the embedding row and the position go up, and only the logits row comes back. Nothing moves between the host and the device inside the layers.
    - Rows are byte-identical to the forward without it: across prefills, single steps, chunks after steps, and steps the device declines (a LoRA adapter, an expert-selection observer). The same holds from position 0, and with two server slots stepping at once (the step holds the device copy's lock throughout).
    - The fit counts its device memory: a few MB on the shared copy, and each slot's post-convolution histories.
    - The device never flushes subnormals to zero, while the default build runs the host with flush-to-zero and denormals-are-zero on. So the device's arithmetic is the one the host kernels are checked against with those modes off: the tests compare these operations that way.
    - `RUNNER_INKLING2_CUDA_TEST_NO_STEP=1` (test-only) keeps every position on the previous route.
