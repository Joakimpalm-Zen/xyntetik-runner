- **`--train-gpu` runs a resident step's head and optimizer on the device too, and a default build's adapter is now a T3 build's, byte for byte, for a constant learning rate** (R8.24.1, list B: R3 and R4).
  - Limits first:
    - A default build's fresh adapter changes once, the CPU trainer's included. Its init scale 1 / sqrt(n) came from a fast reciprocal square root under `-ffast-math`, one bit off the rounded quotient at n 2560 (Qwen3-4B's Q, K, V, gate and up). From this version a default build's fresh adapter is the strict build's (`make T3=1`). The strict build's adapters do not change.
    - The one-sha claim is for a constant learning rate. The schedule (`--lr-schedule cosine`, `--lr-warmup`) is computed on the host in double and is not held to it.
    - A and B come back to the host once a step (66 MB on Qwen3-4B at rank 8). Nothing is resident across steps.
    - The step log's gradient norms are the host's code on its copy of the gradients, so a default build logs them as its CPU trainer and `RUNNER_TRAIN_RES_ADAM=0` do (a strict build's in a T3 build). The norms are in the step log only, not in the training record, so a replay compares nothing they changed.
    - A training record made by an earlier default build does not replay on this one. `runner attest replay` refuses it before training, naming the field: `MISMATCH determinism: expected cpu-t3-exact (or --allow-same-binary), got cpu-same-binary`, and with `--allow-same-binary` `MISMATCH build.binary_sha256`. A `--train-gpu` record never replays (`gpu-within-tolerance`).
    - One host measured: an RTX 5070 beside a Ryzen 7 7700X, Windows 11, Qwen3-4B Q4_K_M.
  - The head (R3): on each round's scored rows, the output norm, the logits, the transforms, the loss's normalizer and its adjoint run on the device (the lab's B5 twin); only each row's normalizer and target logit come back. A teacher's targets (`--train-teacher`) and `--train-logprobs` keep it on the host, and so does `RUNNER_TRAIN_RES_HEAD=0`.
  - The optimizer (R4): on a step every window of which ran resident, the mean's scale (`--batch`) and AdamW run on the device (the lab's B7 twin `k_tadam` and a new one for the scale), with the moments kept there across steps; the step log's norms and their finite check are the host's code on its copy of the gradients, and the device checks its own copy finite before AdamW. A checkpoint's `.optim` and a host step read them back first, and `--train-resume` takes them up. A gradient that is not finite fails the step before anything is updated. `RUNNER_TRAIN_RES_ADAM=0` keeps the host's optimizer, for comparison. The record's `products` gain `resident_adam_steps`.
  - The host scalars the step still needs (the init scale, alpha over rank, AdamW's bias corrections) are computed as a strict build computes them in every build, under a precise attribute. A digest gate in `test-train-gpu`, which needs no device, holds them to a strict build's values on every compiler CI runs.
  - Measured (the recipe: Qwen3-4B Q4_K_M, the ToolUse record's data, rank 8, ctx 128): the 5-step adapter is dbb2f839... in both builds, as main's strict device-mode adapter; 20 steps and a `--batch 2` step give one file in both builds. A step takes 0.667 s against main's 0.679 s (fc47c78f, the resident step alone): 0.982x [0.977, 0.988], 8 interleaved pairs in one session, the mean of steps 2 to 20. R3 alone took 0.651 s; the optimizer on the device costs 1.023x [1.020, 1.027] of that.
