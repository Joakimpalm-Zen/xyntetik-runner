- **`--train-gpu` runs a resident step's head and optimizer on the device too, and a portable-math build's adapter is now the strict build's, byte for byte, for a constant learning rate** (R8.24.1, list B: R3 and R4).
  - Limits first:
    - The one-sha claim is for a build whose host math is portable (`--caps` reports `"math": "portable"`): a Windows default build, a build made with `PORTABLE_MATH=1`, and a strict build (`make T3=1`). A Linux or macOS default build keeps the C library's math (`"math": "libc"`), and the host's side of the forward differs with it from step 1's loss on. Such a build trains a correct adapter of its own, within rounding of the strict build's as before, not the strict build's bytes.
    - A default build's fresh adapter can change once, the CPU trainer's included: its init scale 1 / sqrt(n) is now computed as the strict build computes it. On the Windows build it moved: it came from a fast reciprocal square root under `-ffast-math`, one bit off the rounded quotient at n 2560 (Qwen3-4B's Q, K, V, gate and up). The strict build's adapters do not change.
    - The one-sha claim is for a constant learning rate. The schedule (`--lr-schedule cosine`, `--lr-warmup`) is computed on the host in double and is not held to it.
    - A and B come back to the host once a step (66 MB on Qwen3-4B at rank 8). Nothing is resident across steps.
    - The step log's gradient norms are the host's code on its copy of the gradients, so a default build logs them as its CPU trainer and `RUNNER_TRAIN_RES_ADAM=0` do (a strict build's in a T3 build). The norms are in the step log only, not in the training record, so a replay compares nothing they changed.
    - A device failure in the middle of the optimizer's update is not undone in memory (A, B or the moments can be part-updated): the run fails at that step and writes no checkpoint of it.
    - A training record made by an earlier default build does not replay on this one. `runner attest replay` refuses it before training, naming the field: `MISMATCH determinism: expected cpu-t3-exact (or --allow-same-binary), got cpu-same-binary`, and with `--allow-same-binary` `MISMATCH build.binary_sha256`. A `--train-gpu` record never replays (`gpu-within-tolerance`).
    - Two device classes measured: an RTX 5070 beside a Ryzen 7 7700X under Windows 11, and a CUDA slice (sm_120) under Linux; Qwen3-4B Q4_K_M.
  - The head (R3): on each round's scored rows, the output norm, the logits, the transforms, the loss's normalizer and its adjoint run on the device (the lab's B5 twin); only each row's normalizer and target logit come back. A teacher's targets (`--train-teacher`) and `--train-logprobs` keep it on the host, and so does `RUNNER_TRAIN_RES_HEAD=0`.
  - The optimizer (R4): on a step every window of which ran resident, the mean's scale (`--batch`) and AdamW run on the device (the lab's B7 twin `k_tadam` and a new one for the scale), with the moments kept there across steps; the step log's norms and their finite check are the host's code on its copy of the gradients, and the device checks its own copy finite before AdamW. A host step reads the moments back first, and so does a checkpoint, before it installs anything: a pull that fails leaves the previous checkpoint's adapter and `.optim` as they were, byte for byte, and fails the run (`nothing written for step N`). `--train-resume` takes them up. A gradient that is not finite fails the step before anything is updated. `RUNNER_TRAIN_RES_ADAM=0` keeps the host's optimizer, for comparison. The record's `products` gain `resident_adam_steps`.
  - The host scalars the step still needs (the init scale, alpha over rank, AdamW's bias corrections) are computed as a strict build computes them in every build, under a precise attribute. A digest gate in `test-train-gpu`, which needs no device, holds them to a strict build's values on every compiler CI runs.
  - Measured (the recipe: Qwen3-4B Q4_K_M, the ToolUse record's data, rank 8, ctx 128): on the RTX 5070 the 5-step adapter is dbb2f839... in the strict build and the Windows default build, as main's strict device-mode adapter; 20 steps and a `--batch 2` step give one file in both. On the Linux slice the strict build and a `PORTABLE_MATH=1` build give the same 5- and 20-step files, and the libc-math default build others (c8132a46..., a61094f9...). A step takes 0.667 s against main's 0.679 s (fc47c78f, the resident step alone): 0.982x [0.977, 0.988], 8 interleaved pairs in one session, the mean of steps 2 to 20. R3 alone took 0.651 s; the optimizer on the device costs 1.023x [1.020, 1.027] of that.
