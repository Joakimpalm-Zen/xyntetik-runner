- **The rope position table is computed the same way in every build, so a default build's output can change once in its last bits, and a Linux default build now trains the strict build's `--train-gpu` adapter** (R8.30).
  - **Limits first:**
    - Output bytes can change once on a default build of Linux or macOS, for a model with rotary positions, on the CPU and on the GPU: the table's last bits change, and everything after it with them. A Windows default build, a `PORTABLE_MATH=1` build and a strict build (`make T3=1`) already had this table and do not change.
    - Which models move depends on the build. On Linux every rope model's table moved. With Apple clang the table was already equal at head dimensions 32, 48, 64, 128 and 256 for bases 10000 and 1000000 (one entry of 128 differs at base 10000, dimension 256), and differed in 7 to 31 entries at dimensions 80, 96, 160 and 192, and in one or two entries at base 500000.
    - A persisted prefix store, automatic preamble snapshots and session images made by an earlier release are misses or resume their own rows only, as after any change of the source revision (their keys carry it).
    - The training claim is one measurement: Qwen3-4B Q4_K_M, cross-entropy, a constant learning rate, on two libc-math Linux builds. The rest of a libc-math build's host math is still the C library's.
    - The other load-time constants of the rope setup (the YaRN correction and attention factors, which call `logf`) are as they were.
  - **What was wrong:** `rope_setup` filled the model's inverse-frequency table, base^(-2j/dim), with `powf` in a loop. Under `-ffast-math` gcc vectorizes that loop into the C library's vector `powf` (`_ZGVbN4vv_powf` and its wider forms), whose last bits are not the scalar function's, and the exponent's division is free to become a multiplication. So a Linux default build's table differed from a strict build's, depended on the installed C library, and moved step 1's loss of a `--train-gpu` run by 2.6e-4 relative (0.676102 against 0.676281), which is why such a build trained another adapter than a strict build.
  - **The fix:** `model_rope_inv_freq_fill` computes both tables (the model's and gemma's local set) with the exponent as written and the portable power function's steps, under the precise attribute the trainer's host scalars already use. About 64 values at load: no cost per token or per step.
  - **Tests:** `test-train-gpu` (no device needed, so every CI host runs it) holds the table at six bases and eleven dimensions to the digest a strict build gives, and in a strict build to that build's own `powf`. It failed on a default build before the fix (Apple clang: digest c5d3092ed97d83a2 against 5e85efccb2d74f26).
  - **Measured:** with the portable function at the two sites, a libc-math Linux build (gcc 15.2, glibc 2.39) gave step 1's loss 0.676281 and the strict build's adapters after 5 and 20 steps (dbb2f839..., 3db68802...); without it, c8132a46..., byte for byte what another libc-math Linux build (gcc 13.3) gave.
