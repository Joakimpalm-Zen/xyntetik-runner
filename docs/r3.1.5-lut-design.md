# R3.1.5: low-bit CPU prefill, design note

Status: draft for the coordinator (2026-11-01). Premise checked; no code yet.

## The gap, measured

CPU prefill of 512 tokens at 4 threads on an Apple M1 (8 GB), `Qwen3-0.6B-Q8_0.gguf`:

- Runner (`--bench-json --gpu off`, main at c37ddcf8): **91 tok/s**.
- llama.cpp as Homebrew ships it (ggml 0.22.0, `llama-bench -p 512 -n 0 -t 4 -ngl 0`): **310 tok/s**.

That is 29% against the plan's KPI of at least 50%. The Homebrew build loads its BLAS backend (Apple's Accelerate),
so its prefill GEMMs run on the M1's matrix unit. A llama.cpp build without BLAS uses its own int8 kernels instead.
That reading is owed before any number is stated as the gap to llama.cpp's own arithmetic.

## Where Runner's prefill time goes

For a batch of 8 or more rows, `model.c` dequantizes each weight row to float32 once and runs float32 FMA register
tiles (`vec_dot_f32_tile`: 8 x 3 and 4 x 4 on NEON) against the activation columns. Each multiply-add is one 4-lane
float FMA. The arithmetic is float32 end to end, and every output is bit-identical to the one-column dot.

There are two kinds of lever, and they differ in what they give up:

| Route | Arithmetic | Peak on the M1, per core (order of magnitude) | Contract |
|---|---|---|---|
| Today: dequantize to f32, NEON FMA tiles | f32 x f32 | 1x | bit-identical to the solo dot |
| A. f32 GEMM on the matrix unit (Accelerate `cblas_sgemm` on dequantized tiles) | f32 x f32, other order | several x | tolerance-class (reassociation only) |
| B. int8 activations, `SDOT` tiles (llama.cpp's own CPU kernels) | int8 x int8, int32 accumulate | about 4x | tolerance-class plus activation rounding |
| C. Table lookup (T-MAC): the activations' partial sums tabulated, the weight bits as `TBL` indices | int8/int16 tables | scales with 1/bits; T-MAC reports up to 4x over llama.cpp at 2-4 bits | tolerance-class plus activation rounding |

## What each route is for

- **A is the Mac lever, and the cheapest.** It keeps float32 arithmetic and changes only the summation order. That is
  the same trade the Metal prefill tiles made in #517, and it answers to the same D1 rows against float32. It is
  Apple-only, and it is likely what the 310 tok/s above is made of.
- **B is the portable lever for 8-bit and 4-bit weights.** It is what llama.cpp does without BLAS, on x86 and ARM
  alike. Runner already has the pieces for the decode dot (`vec_dot_i8`, `RUNNER_CPU_I8`, `SDOT` on NEON) and the
  0/64-flip gate (R3.2) that governs promoting it. The CPU int8 route failed that gate on Flash-Next (3/64), so
  admission is per (type, architecture), as the plan says.
- **C is the low-bit lever (R3.1.5 as written).** It wins as the bit width falls (2-3 bit, IQ1-IQ3, ternary), which is
  what the keep-N, R4.9.1 and sub-4-bit files need. At 8 bits it loses to B. It is the most code: table construction
  per activation group, a layout of the weight bits per type, and the K-quant scale handling.

## Proposal

1. **Owed first:** the llama.cpp CPU number without BLAS, on the M1 and on the lab's x86 cores. That fixes the real
   gap to llama.cpp's own arithmetic (B) and separates it from Accelerate (A).
2. **Then, in order of gain per day:**
   1. A on Apple, behind a switch, held to D1 rows like #517.
   2. B as the prefill tile for Q8_0 and Q4_K, NEON and AVX2, behind R3.2's gate.
   3. C for the 2-3 bit types once B's tile and gate exist, since C reuses B's activation quantization and gate.
3. **KPI as the plan states it:** at least 50% of llama.cpp on the M1, and at least 40% on the Threadripper, each
   measured against both llama.cpp builds (with and without BLAS), with the comparison named.

## Questions for the coordinator

- Should C wait for B, or does the owner want C first for the low-bit artifacts even if B is the larger win at 4-8 bits?
