# R3.14: CUDA prefill on int8 tensor cores (2026-11-03)

**Unflattering first: the route does not pass its own gate on every file, and it stays opt-in.** On Qwen3-0.6B Q8_0,
`RUNNER_CUDA_I8=1 ./test-tc-tol` fails: its 32 greedy tokens after a 128-token prompt diverge from the scalar route
at token 3, where the scalar route's own margin is 0.00008 of the logit range. After a 1,965-token prompt the 32
greedy tokens differ from the default (fp16 tensor-core) route on three of four files; only Qwen3-4B Q4_K_M stays
identical. The read against the publisher's float32 model (D1) did not run (below). Against that, prefill is faster
on every file: the int8 GEMMs take 1.66x less time than the fp16 route's on Q8_0 and 1.18x less on Q4_K_M, and no
file flips a top-1 token in the 64 teacher-forced positions of the gate.

## What the route does

`RUNNER_CUDA_I8=1`, on a compute capability 8.0+ device, sends a prefill GEMM to `kernels_i8.cuh` wherever the
tensor-core route is on for the type and the type has a kernel (Q8_0, Q4_K, Q6_K). The window's activations are
quantized once a matvec to int8 per 32-element block (amax / 127, with the block's sum). The weights' own integer
quants go to the tensor cores as they are (`mma.sync` m16n8k32; m16n8k16 for Q6_K's 16-element scales), and each
block's int32 sum folds into fp32 as `ws * dx * dot - wm * xs`. Decode (one column) is untouched.

Since the first cut (8e891044), two changes to the kernel, both measured with Nsight Compute on the RTX 3070:

- The block scales of a 32-deep step are read into registers once per step instead of once per `mma`.
- Q8_0 copies a stage's weights cooperatively: consecutive threads take consecutive 4-byte words of a row (17 words
  for the 68 bytes of two blocks), so a warp's load covers contiguous bytes. The tile is then repacked from shared
  memory. On Qwen3-1.7B Q8_0 the GEMM time fell from 302 to 203 ms. The same copy measured slower for the K-quants
  (Q4_K 395 against 341 us a launch, Q6_K 374 against 213 us, also with word-aligned funnel-shift reads), so Q4_K
  and Q6_K keep the first cut's per-thread loads.

The pinned PTX (`src/kernels_ptx80.h`) is regenerated by the pinned toolchain (`tools/ptx-toolchain/make-ptx.sh` in
Docker). It carries no `used_bytes_mask` pragma and assembles at `.version 7.8` with `ptxas -arch=sm_86`. Only the
compute_80 module changes.

## Speed

The Windows CUDA host, RTX 3070 (8 GB, sm_86), driver 596.36. Prefill of `val171/nvfp4-prompt.txt` (1,965 tokens;
1,925 on Llama), `-n 32 --temp 0 -c 4096`, the default route and `RUNNER_CUDA_I8=1` alternated, three rounds, warm
JIT cache. Every round sits within 0.5% of the median.

| File | Default, prompt tok/s | `RUNNER_CUDA_I8=1` | Gain | Decode tok/s (both) |
|---|---|---|---|---|
| Qwen3-0.6B Q8_0 | 7,223 | 8,503 | +18% | 253 / 252 |
| Qwen3-1.7B Q8_0 | 3,839 | 5,207 | +36% | 145.8 / 145.3 |
| Qwen3-4B Q4_K_M | 2,162 | 2,330 | +8% | 93.2 / 93.2 |
| Llama-3.2-3B-Instruct Q4_K_M | 2,645 | 2,953 | +12% | 123.2 / 123.3 |

The GEMM phase alone (`RUNNER_CUDA_PROFILE=1`, the prefill's `matvec` line, best of 3): Qwen3-1.7B Q8_0 337.6 ms
default against 202.9 ms int8 (1.66x); Llama-3.2-3B Q4_K_M 499.5 against 424.4 ms (1.18x). The rest of a prefill
(attention, norms, the activation quantizer) is unchanged, so the end-to-end gain is smaller.

Nsight Compute on the Q8_0 kernel before the cooperative copy: 16.7% occupancy at 129 registers, L1 at 76%, the
integer MMA pipe at 12%. A run with a fake one-row weight load halved the kernel time, which is what pointed at the
weight load. `__launch_bounds__(256, 2)` doubled occupancy and gained nothing, so it is not in.

## The tolerance gate

`RUNNER_CUDA_I8=1 ./test-tc-tol FILE`: the int8 route at batch 64 against the scalar route at batch 64, 64
teacher-forced positions, then 32 greedy tokens after a 128-token prompt.

|---|---|---|---|---|---|
| Qwen3-0.6B Q8_0 | `9465e63a...` | 0.00095 | 0/64 | diverged at token 3 | FAILED |
| Qwen3-1.7B Q8_0 | `061b54da...` | 0.00077 | 0/64 | identical | ok |
| Qwen3-4B Q4_K_M | `7485fe6f...` | 0.00087 | 0/64 | identical | ok |
| Llama-3.2-3B-Instruct Q4_K_M | `6c1a2b41...` | 0.00040 | 0/64 | identical | ok |

The long-prompt runs in the speed table compare the two routes' greedy text after 1,965 tokens. Qwen3-0.6B, Qwen3-1.7B
and Llama-3.2-3B differ (Llama from its first token); Qwen3-4B Q4_K_M is identical. `make test-cuda-i8` (the Q8_0,
Q4_K and Q6_K fixtures, the int8 kernels required to run) passes, 28 int8 dispatches each.

## Against the publisher's float32 model (D1): not run

The score files are made: `RUNNER_SCORE_CHUNKED=1 RUNNER_SPEC_BATCH=64 runner --score 20 -c 8192` on
`tests/fixtures/gold-corpus-2k.txt`, Qwen3-0.6B Q8_0, default and int8 (8,007 positions each, 24,625
int8 GEMMs on the int8 side). The read with `scripts/gold-logits.py` against `Qwen/Qwen3-0.6B` at `c1899de2`
did not finish. It was one float32 forward over 4,009 tokens (about 2.4 GB of logits plus attention buffers), and
the harness on the 16 GB host stopped it for low memory. The peak was not measured, so that cause is not confirmed.
The obvious rerun is a chunked read (`logits_to_keep`, or fewer positions per forward). The route's verdict does not
wait on it: it fails `test-tc-tol` on Qwen3-0.6B, so it ships opt-in either way.

## Not in this change

- R3.14.1: promotion per type and architecture past the 0/64-flip gate, and the D1 read rerun chunked.
- K-quant speed: Q4_K and Q6_K gain 1.18x on the GEMM. A load that suits their layouts is open.
- Other architectures: only sm_86 is measured. Below compute capability 8.0 there are no int8 kernels, and the flag
  leaves the fp16 tensor-core route in place.
