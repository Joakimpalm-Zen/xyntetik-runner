# CUDA kernels for the codebook i-quants (2026-09-14)

Trigger: `Joakimpalm-Zen/Qwen3.8-27B-GSQ-RCO-IQ3_S-recovered-GGUF` did not run
on CUDA. The file is a mixed-type quant (IQ3_S 144 tensors, IQ4_XS 96, BF16
96, IQ3_XXS 78, Q4_K 39, IQ2_S 17 including `token_embd.weight`, Q2_K 13,
IQ2_XS 9, IQ2_XXS 5, IQ1_M 1, F32 353), and the CUDA backend admits a model
whole or not at all, so its first IQ tensor sent the entire model to the
CPU: 0.5.2 on the Blackwell slice with `--gpu-layers 40` says `gpu: tensor
blk.0.ffn_gate.weight uses IQ2_XS, which has no CUDA kernel`, and without
a split it stops one step earlier at the VRAM ask for the whole 11.8 GB
file. The same shape had already cost the 2026-09-06 admission report its
Qwen3.8 UD-Q4_K_M row (four IQ3_S tensors, "not measurable").

## What was built

Fourteen kernels in `src/kernels.cu`, `k_mv_<type>` (one column,
generation) and `k_mv_<type>_b` (prefill tile) for IQ1_S, IQ1_M, IQ2_XXS,
IQ2_XS, IQ2_S, IQ3_XXS and IQ3_S, registered in `src/cuda.c`'s admission
switch and kernel table. Each walks its block exactly as the matching
`dq_*` decoder in `src/quants.c` does, one lane per 256-weight block, in the
shape of the existing warp-per-row matvecs; the codebook grids are the
formats' own tables, copied from `src/quants_iq_grids.h` and held equal by
`tests/test_cuda_iq_grids.py`, and the 7-bit sign index of IQ2_XXS,
IQ2_XS and IQ3_XXS expands arithmetically (`ksigns_iq2xs[i]` is `i` with
its odd parity in bit 7, checked for all 128 entries by the same test). The
PTX was generated by CUDA 13.3 on the Windows box, the project's PTX
compiler; the per-kernel diff against the previous header adds the fourteen
kernels and six tables and changes no other kernel's body.

The rule of the house applies: llama.cpp is the interoperability oracle
and the source of the format definition (the tables), not the blueprint.
Nothing was ported from ggml-cuda; the kernels are device twins of the
runner's own CPU path.

Every format the loader reads now has a CUDA kernel, so the "no CUDA
kernel" diagnostic can no longer be reached by a real file. It is kept
under test through `RUNNER_CUDA_INIT_INJECT_FAILURE=no-kernel:<TYPE>`, the
same mechanism as the existing shared-pointer-tables injection.

## Gates

**Fixtures.** `tests/test_iquants.py` quantizes the 256-wide fixture into
the seven llama-quantize i-quant recipes with an imatrix. The union of the
files' real tensor types covers all seven decoders (the IQ2_S recipe
stores IQ2_XS and IQ3_S tensors on this fixture; the IQ3_XXS recipe stores
four IQ2_S ones). Two legs per file:

| leg | box | result |
|---|---|---|
| CPU vs llama-server b10353, teacher-forced log P(token \| prefix), 16 positions | Blackwell (CPU) | 7/7 within 0.05; worst 0.0163 (IQ2_XS), per-file mean 0.003 to 0.005 (llama.cpp's Q8_K activation quantization against the runner's f32 activations) |
| CPU vs CUDA logit identity, `test-gpu-identity`, 24 positions, prefill batch 32 | RTX PRO 6000 Blackwell MIG slice | 7/7 ok; worst relative deviation 2.18e-6 (IQ3_XXS), the rest 4e-7 to 1e-6 (limit 2e-3) |
| same | RTX 3070 (ZEN-GAMING, Windows, CUDA 13.3) | 7/7 ok; worst 2.54e-6 (IQ3_XXS); single-token forwards (`0 1`) on IQ3_S 6.7e-7 and IQ1_M 2.0e-6 |

**Real file.** `scripts/cpu_cuda_check.py` on the GSQ-RCO file
(sha256 `873df48d`, the card's `output_sha256`), nine prompts spanning 5 to
96 tokens at 128 generated tokens, `RUNNER_CUDA_TC=0`, 40 of 64 layers
(7.4 GB) on the Blackwell slice and the CPU running the rest: **9/9 exact,
0 near-ties tolerated** (`cuda-iquants-evidence/cpu_cuda-qwen38-27b-gsq-rco-iq3s-blackwell.json`,
device log beside it). The split is real and recorded; a full-offload claim
is not made.

## The gate that was vacuous

`tests/test_iquants.py` had built its files from the default 64-wide
fixture since the i-quant port of 2026-08-11. A codebook block is 256
weights, so llama-quantize silently substituted IQ4_NL and Q4_0 for every
tensor; the seven "i-quant" files carried no i-quant block, and the
byte-identical greedy comparison it reported was IQ4_NL against IQ4_NL.
The real-file greedy anchor on the bartowski Muse-Glimmer IQ3_XXS file
(`docs/muse-glimmer-cert-2026-08-11.md`) was the gate that held for the
CPU decoders. The test now uses the `--wide` fixture, reads each file's
real tensor types, fails if the union misses a type, and compares
per-position logprobs against llama-server's raw logits (n_probs over the
whole vocabulary) rather than greedy text, because on the sparsest
fixtures the greedy token is a lone byte above 0x7F that llama-server's
content parser refuses to return.

## Not claimed

- No llama.cpp column on the real file in this pass; the CPU decoders are
  unchanged and keep their earlier anchor.
- Metal has no kernels for these types; that backend still declines the
  file, naming the tensor.
- No performance claim. The kernels are the generic warp-per-row shape;
  the coalesced GEMV, tiled GEMM and tensor-core paths do not cover them.
