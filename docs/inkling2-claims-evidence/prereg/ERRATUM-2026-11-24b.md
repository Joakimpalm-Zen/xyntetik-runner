## The finding

Runner's receipt lists the generated ids WITHOUT the stop token, while the same record's response reports it (`choices[0].stop_token_id`). The committed Runner records were written by `claim_client.py` version 1, which stored the receipt's ids as `gen_ids`. So each of Runner's 58 answers that stopped before 256 tokens records `gen_ids` ending one token short of `200006`:
- 35 of them finished with `stop`;
- 23 with `tool_calls`.

PREREG 1.3 requires `g_{L-1} == 200006` for an answer that stopped, so all 58 count as incomplete. Of them:
- 54 agree with the reference at every recorded position;
- the final stop position was never teacher-forced.

llama.cpp's client stores the stop token, so its records are complete.

## The correction

1. **Runner's complete generation is read from each committed record's own fields.**
   - `gen_ids` plus `[choices[0].stop_token_id]` when the response reports a stop token and the ids do not already end with it.
   - This is `claim_client_v2.py`'s `with_stop()` (committed `b98a60442`), applied by `tools/erratum3_complete.py`.
   - The derived file is `records/claim1-runner-ref-erratum3/answers.jsonl` (`6ee13d1c...`): 58 records get `200006` appended and 42 are unchanged.
   - The committed records (`records/claim1-runner-ref/answers.jsonl`, `c6cb0622...`) are read, never written.
2. **The 58 changed sequences are teacher-forced afresh** with `tools/verify_tf.py` version 2 (unchanged, `6e38f573...`). This checks the reference's prediction at each one's final stop position, together with every earlier position.
   - The 42 unchanged sequences and llama.cpp's 100 are the SAME inputs as in the first run.
   - Their results are reused from the first run's `records/verify-claim1/claim1.seqs.jsonl`, the same tool on identical keys. The reference was shown deterministic: the control's all-rows rows reproduced bit for bit across two runs.
   - The run's output is `records/verify-claim1-erratum3/`.
3. **`tools/claim1_stats.py` (unchanged) computes the erratum-3 figures** from that output. They are reported BESIDE the pre-registered figures above, labelled "erratum 3, decided after the verdicts".
4. **Runner's future pre-registered cells use `claim_client_v2.py`,** which records the stop token, so they need no such reading.
5. **Nothing else changes:** no setting, prompt, metric, interval method, decision rule, claim wording, or llama.cpp record.
